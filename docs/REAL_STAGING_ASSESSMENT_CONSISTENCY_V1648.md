# v164.8 — Reconcile real saved Inbox assessments before deduplication

A read-only Supabase aggregate on 17 November 2026 found nine monitoring campaigns, 786 captured social records, 636 campaign-evidence links across 616 original sources, 599 latest campaign-source assessments, 37 unassessed links, 468 relevant campaign-source links across 463 original sources, and one original relevant source with conflicting saved sentiments across campaigns. No duplicate campaign/source pairs were present. These counts cover the entire database and **must not** be confused with the narrower permission-scoped recent Inbox window.

Previously `compile_inbox_findings` selected one preferred relevant campaign assessment per original source. Conflict detection applied later to the grouped findings and therefore could miss disagreement between two campaigns' saved assessments. v164.8 introduces `inbox_saved_link_consistency` to compare the already-loaded, permission-scoped Inbox rows **before** that selection. For each source, the helper compares the latest available saved sentiment within each authorized campaign and counts distinct sources with cross-campaign disagreements. It does not output original source IDs, post text, campaign IDs or officer identities. The existing Radar response has a bounded `saved_link_consistency` field describing selected-feed scope, number of relevant links, multi-campaign sources, sentiment conflicts and the recommended officer follow-up.

An absence of conflict in the recent, relevance-only Inbox window does not imply zero disagreements across all campaigns or across unassessed records. Nothing is automatically reclassified; officer overrides remain authoritative for their original campaign record. No schema changes, DB writes, additional DB queries, provider/model calls or new developer QA UI. Automated tests cover conflicting and consistent campaign assessments, latest saved version behavior, duplicates, rejected records, immutability and privacy.
